# 输出格式

只有一条硬要求：**给参考原文**。结构按题型，没有的段直接省略，不写"无"。

## 硬规矩

1. 每条依据两行：

   ```
   《书名》> 章节 > 页标题
   原文: <工具 src: 的原值>
   ```

   - 书名/章节/页标题来自 `search` / `page` 输出；`原文:` 原样抄 `src:`（镜像、官网、包内路径或 PDF/Excel 定位）。
   - 只写书名章节、没有 `原文:` 行 = 不合格。
   - 通常 1–3 条，跨章节最多 5 条。

2. 界面名、命令名、配置项、handler/工具/首选项名，一律官方英文原文，不自造中文术语。

3. 分清"帮助里说可以这样做"（产品能力）与"你们站上是否已这样配"（本技能不知道，查 `tc-biz`）。

## 三种骨架

### 事实 / 查找（一个名字、一个值、在哪配）

一句话答案 → 依据 →（涉及许可/模块时）一句条件。通常 4–6 行。

```
远程签入时新加组件由 TC_remote_checkin_assy_option 控制
（General / Integer / 保护范围 User / 默认 1）。

《Administration Data Documentation》> Preferences > TC_remote_checkin_assy_option
原文: http://127.0.0.1:5000/documentation/external/PL20250129156809455/en-US/AdminDataReport/Preferences/....

注：这是报告快照默认值；站上当前值用 tc-biz 查。
```

`handler` / `util` / `pref` / `savedquery` 的结果默认走这一种。
`pref` 带 `⚠ 已弃用` 时必须写"不要在新配置里使用"；带 `⚠ 内部项` 的注明"内部项，不建议配置"。

### 操作 / 流程（怎么做）

结论 1–2 句 → 编号步骤（有先后编号，并列用列表，数量写清）→ 依据 →（找不到时）缺口。

缺口写三件事：试过哪些英文词、最接近的相邻主题、下一步去哪查。

### 能力判断（能不能做、要不要开发）

结论分档：原生已满足 / 配置或模块可行（写条件）/ 需开发（写差什么）/ 证据不足。后接依据；有缺口再写缺口。

## 反例

- ✗ "可以在系统里配置" —— 没给界面和配置项。
- ✗ "参考官方文档" —— 没出处。
- ✗ 只写书名章节，不写 `原文:` 行。
- ✗ 把两本书的说法拼成一条步骤 —— 会造出产品里不存在的流程。
- ✗ 自造中文术语（"所有者转移"）而不用原文（`change ownership`）。
- ✗ 为凑格式写"缺口：无""适用条件：无"。
